# UrbanAgent Data Source License And Usage Policy

Updated: 2026-07-31.

Status: `PROPOSED POLICY`.

Implementation status: `NOT ENFORCED BY CODE`.

This document defines the minimum legal, licensing, storage, attribution, and
data-governance requirements for any external source considered by UrbanAgent.

It is an engineering and product-governance policy, not legal advice.

A current license or contract review is required before any source is used.

## 1. Core Rule

No external data source may be:

- ingested,
- persisted,
- cached,
- displayed,
- redistributed through an API,
- exported,
- sold,
- used for training,
- used to create commercial derived data,

unless the intended use is permitted by the source license or contract.

Historical assumptions about a provider are not sufficient. The active terms
must be reviewed at source-onboarding time.

## 2. Source Usage Classes

Every source must be assigned one usage class.

### 2.1 `PERSISTENT_OPEN`

The source may be persistently stored and used under a compatible open-data
license.

Requirements may still include attribution, notice retention, database-license
obligations, share-alike obligations, and source-link preservation.

### 2.2 `LICENSED_PERSISTENT`

A commercial or partner agreement permits persistent storage for defined fields
and uses.

The contract must define permitted fields, territories, retention, display,
redistribution, derivative works, and termination behavior.

### 2.3 `REQUEST_TIME_RESTRICTED`

The source may be queried for immediate or short-lived product use, but its
content must not automatically become permanent canonical data.

The registry must define allowed cache duration, fields that may be retained,
permitted identifiers, attribution, deletion behavior, request limits, and
cost.

### 2.4 `USER_OR_PARTNER_SUBMITTED`

The data is supplied directly to UrbanAgent by a user, business, partner, or
operator.

Requirements include submission agreement, rights confirmation, consent where
relevant, moderation, correction workflow, deletion workflow, and privacy
classification.

### 2.5 `URBANAGENT_DERIVED`

The value is generated by UrbanAgent from permitted inputs.

Derived data must retain input references, method version, confidence,
timestamp, uncertainty, and restrictions inherited from source contracts where
applicable.

Derived data is not automatically free of source restrictions.

### 2.6 `PROHIBITED`

The source must not be used for ingestion.

Examples include competitor application pages used as substitute POI
databases, scraped commercial map content without permission, copied review
datasets without redistribution rights, leaked datasets, sources with unclear
ownership, and sources whose terms prohibit the intended use.

## 4. Approval Status Values

Recommended source approval statuses:

- `DISCOVERY_ONLY`
- `SPIKE_PROPOSED`
- `LICENSE_REVIEW_REQUIRED`
- `CONTRACT_REVIEW_REQUIRED`
- `APPROVED_FOR_DRY_RUN`
- `APPROVED_FOR_RUNTIME`
- `REQUEST_TIME_ONLY`
- `NOT_APPROVED_FOR_CANONICAL_IMPORT`
- `PROHIBITED_AS_DATA_SOURCE`
- `RETIRED`

Only `APPROVED_FOR_RUNTIME` permits production runtime use, and only for the
fields and uses recorded in the registry.

## 5. Provider-Specific Guardrails

Google Places, Foursquare, Tripadvisor, booking providers, transport providers,
and other commercial providers must be treated as restricted until an active
contract proves otherwise.

Provider photo URLs, review text, ratings, opening hours, phone numbers,
websites, and current operating status may have different storage and display
rules. Each field must be classified independently.

Wanderlog, Mindtrip, Layla, Yelp pages, Tripadvisor pages, Google Maps pages,
and similar competitor or commercial product pages are not approved as scraped
POI sources.

Competitor products may be used for product-pattern benchmarking only, unless
a separate license explicitly approves a data use.

## 6. Attribution And Display

If attribution is required, the source registry must define:

- exact attribution text,
- attribution link,
- display placement,
- whether attribution is required per POI, per screen, or per dataset,
- whether attribution must survive exports or shared links.

Frontend, API, and export behavior must not remove or hide required
attribution.

If attribution requirements cannot be satisfied in the current product surface,
the source must not be used in that surface.

## 7. Storage, Cache, Refresh, And Deletion

Every source must define:

- whether persistent storage is allowed,
- whether short-lived cache is allowed,
- maximum cache duration,
- refresh interval,
- stale-record handling,
- user or provider deletion flow,
- termination behavior if the agreement ends.

Expired or deleted restricted data must not remain in public API responses,
fixtures, Git bundles, backups intended for distribution, or derived exports.

## 8. Machine Learning And Derived Use

Machine-learning use is prohibited unless the license or contract explicitly
allows the intended training, evaluation, embedding, feature extraction, or
derived-data use.

Derived data must retain evidence references and inherited restrictions when a
source contract requires it.

An LLM explanation may summarize permitted evidence, but it must not invent
missing ratings, reviews, opening hours, addresses, coordinates, freshness, or
provider identifiers.

## 9. Security And Privacy

Source credentials, API keys, tokens, raw provider payloads, restricted review
or photo data, and non-public entity-resolution evidence must not be committed
to Git, included in Git bundles, stored in public fixtures, or exposed through
public APIs.

User or partner submissions must include privacy classification, consent or
agreement status, moderation status, correction workflow, and deletion
workflow.

## 10. Dry-Run Requirements

Every approved source spike must run in an isolated development environment
and produce:

- exact-match report,
- fuzzy-match report,
- ambiguity report,
- probable-new-entity report,
- duplicate report,
- source-conflict report,
- license report,
- attribution report,
- field-completeness report,
- stale or removed record report,
- cost report,
- rollback plan.

No spike may modify the canonical CSV, production database, Firebase
production data, or default runtime repository.

## 11. Phase 2 Freeze

During active Phase 2 Traveler API v2 work:

- the canonical CSV remains unchanged,
- the canonical SHA-256 remains unchanged,
- application POI count remains `4166`,
- Da Nang remains the only supported City Pack,
- CSV remains default runtime,
- PostgreSQL remains explicit opt-in,
- external source ingestion remains out of scope.

Future source work requires a separate approval after the current Phase 2 work
is safely paused or completed.

## 12. Approval Gate

Implementation may begin only after explicit approval of source scope, source
list, license review, storage policy, test environment, entity-resolution
thresholds, reporting format, and no-production-write guardrail.

Required approval phrase:

`APPROVED MULTI-SOURCE POI SPIKE`

Until that approval exists, this document remains policy planning only.
